# 1.3 整体路线图

这节给出全书的施工顺序，让你知道每一步在全局中的位置、为什么这么安排。

## 四步走

```text
第 4 章          第 6 章           第 7 章          第 7.5 节
CPU 参考实现 ──► GPU kernel ──► 宿主程序 ──► 端到端验证
（Rust，可测）   （OpenCL C）     （Rust+opencl3） （wg pubkey）
```

### 第一步：CPU 参考实现（第 4 章）

先用纯 Rust 在 CPU 上写出完整正确的 X25519。这一步没有任何 GPU 的东西，好处是：

- 可以用 `cargo test` 跑 RFC 7748 官方测试向量；
- 可以和成熟的 curve25519-dalek 库**对拍**（同样的输入，两边结果必须逐字节相同）。

CPU 版本就是我们手里的「标准答案」。

### 第二步：GPU kernel（第 6 章）

把 CPU 版本逐行翻译成 OpenCL C，写成 kernel。关键原则是**一一对应**：Rust 里的 `fe_mul` 对应 kernel 里的 `fe_mul`，连变量名都一样。这样翻译出错时容易对照排查。

### 第三步：宿主程序（第 7 章）

GPU 不能自己启动自己，需要 CPU 上的「宿主程序」负责：初始化 OpenCL、编译 kernel、把参数搬进显存、一批批发射任务、把命中的密钥读回来。

### 第四步：验证（贯穿全书）

GPU 代码没法随便打断点，所以正确性靠三层验证兜底：

1. `cargo test`：CPU 实现过 RFC 7748 向量 + dalek 对拍（4.9 节）；
2. `--selftest`：GPU 算 4096 个密钥（默认值，7.4 节的示例显式跑 8192 个），全部与 dalek 逐字节比对（7.4 节）；
3. `wg pubkey`：程序产出的私钥交给 WireGuard 官方工具算公钥，交叉验证（7.5 节）。

三层全过，才能信任搜索结果。

## 为什么是这个顺序

直接在 GPU 上写密码学代码是新手最容易翻车的路：没有调试器、没有打印、一个 bit 错了就是全盘皆错，而且你根本不知道错在哪。先有一份被测试钉死的 CPU 参考实现，GPU 版本就有了可以随时对拍的「裁判」——这就是路线图的核心思想。

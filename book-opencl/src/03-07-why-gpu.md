# 3.7 GPU 为什么适合穷举

这节从硬件角度回答：同样是算 X25519，为什么 GPU 能比 CPU 快几百倍。理解这个，第 6 章的 kernel 写法就顺理成章了。

## CPU 与 GPU 的设计取向

- **CPU**：几个到几十个强大核心，擅长复杂控制流、大缓存、低延迟——「一个博士生做一道难题」；
- **GPU**：成千上万个简单算术单元，共享指令流，擅长对海量数据做同一件事——「一万个小学生做一万道类似的题」。

RX 7900 XTX 有 96 个计算单元（CU）、6144 个流处理器，实测我们的 kernel 能跑到约 10.8 M keys/s——同时有成千上万个候选密钥在流水线上推进。

作为对照：本书的 CPU 参考实现（第 4 章，Rust 直译、未做优化）在同一台机器上单核实测约 55 µs/个，即约 1.8 万 keys/s——GPU 的 10.8 M/s 约为它的 600 倍。注意这是实测口径：优化过的 CPU 实现（如 dalek）会快不少，别拿教科书上「1~2 µs」之类的数字来套我们的直译版。

## work-item 模型

OpenCL 的执行模型（第 5 章细讲）一句话版本：

```text
kernel（同一段代码）
   ├── work-item 0   （gid=0，算候选 0）
   ├── work-item 1   （gid=1，算候选 1）
   ├── work-item 2   （gid=2，算候选 2）
   └── ... 一次发射 2^22 ≈ 400 万个
```

每个 work-item 拿到自己的全局编号 `gid`，从 `gid` 派生出独一无二的候选私钥，独立走完「派生 → X25519 → 前缀比对」全流程。

## 为什么穷举是 GPU 的完美负载

1. **天然并行**：候选之间毫无关系，不需要任何通信——想开几万个就开几万个；
2. **控制流整齐**：梯子是 255 步固定流程、cswap 无分支（3.5 节埋的伏笔），所有 work-item 步调一致，GPU 的「共享指令流」机制零浪费；
3. **算多访少**：每个候选只读几个参数、几乎不写内存，瓶颈在算术单元而不是显存带宽——正是 GPU 的长项；
4. **寄存器够用**：10 个 u64 limb 的中间变量全放寄存器，不碰慢速内存。

反面教材是「分支多、候选之间要交换数据、频繁读写大内存」的任务——那些 GPU 并不擅长，只是我们的任务恰好全避开了。

## 小结

- GPU = 海量简单单元 × 同一段代码 × 不同编号的数据；
- 穷举 vanity 公钥是教科书级的「尴尬并行」负载；
- 3.5 节坚持无分支 cswap，到这一节兑现了它的价值。

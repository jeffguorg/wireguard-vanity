# 8.2 调优方向与练习题

最后一节：几个试过的和没试过的调优方向，以及循序渐进的练习。到这里你已经拥有全部知识，剩下的就是动手。

## 试过的：local_size

`shader.comp` 的 `local_size_x` 试过 64 / 128 / 256 三档：在 RX 7900 XTX 上 128 略优或持平，64 和 256 均无明显提升。结论：这个 kernel 是寄存器/算力受限而不是 occupancy 受限，改 workgroup 大小收益有限。改完记得同步改 main.rs 里两处 `128`（`n / 128` 和 `round_size / 128`）。

## 想清楚的：push constant vs SSBO

种子和前缀现在走 push constant（104 字节，每轮重写一次命令）。替代方案是放进一个只读 SSBO，每轮 `buf.write()` 更新。理论上 push constant 更轻（不需要内存同步），实测对本 kernel 差异可忽略——因为每轮 2²² 次迭代里参数只传一次，传输成本被摊薄到无感。**参数通道的选择在「每轮短」的场景才重要**（比如把 round_log2 调到 16 以下试试）。

## 没试过的：32-bit limb

现在的设计用 64 位 limb（10 × 26/25 bit）。RDNA 的 32 位整数乘法是全速的、64 位是合成的——把表示改成 **20 × u32 limb**（类似 ref10 的 32 位原版），乘法吞吐可能显著提升，但进位链更长、寄存器压力更大。这是最有可能反超 OpenCL 版的方向，也是最硬核的练习。

## 练习题（由易到难）

1. **多结果收割**：`--count 10` 跑 3 字符前缀，观察一轮里多个命中的回收路径（`slot < 64` 闸门）。
2. **改轮大小**：`--round-log2 20` vs `24` 各跑 30 秒，比较速率。解释为什么太大也不好（提示：fence 等待间隔与「找到后多算的浪费」）。
3. **双缓冲流水线**：改 `dispatch`，让第 n+1 轮提交后再等待第 n 轮的 fence（需要两个结果 buffer 轮换）。测量提升。
4. **统计检验**：跑 100 次 2 字符前缀（每次不同 seed0），记录命中所需尝试次数的分布，和几何分布的理论值对比。
5. **硬核**：实现 32-bit limb 版 shader（20 个 u32 limb），保持 CPU 参考实现不动，用 `--selftest` 验证，再测速率。

## 结语

回看全程：你手写了 GF(2^255−19) 的完整算术、Montgomery 梯子、费马求逆，把它翻译进 GLSL，又用 Vulkan 的 instance/device/queue/pipeline/descriptor/push constant/fence 全家桶把它跑在真 GPU 上，最后用三层验证（RFC 向量、dalek 对拍、wg 命令）确保每个比特都对。

这套「CPU 参考实现 → GPU 移植 → 双向对拍」的工程方法，和「limb 表示 + 延迟归约」的密码学实现技巧，迁移到任何 GPU 计算任务都成立。玩得开心，搜到靓号记得炫耀。

# 3.3 大数怎么装进 u64：limb 与 radix 2^25.5

这节解决最具体的表示问题：255 bit 的域元素怎么用一堆 u64 存。这套表示是 CPU 和 GPU 两份代码共同的骨架。

## limb：把大数切成小段

一个 u64 存不下 255 bit，那就用多个。我们把大数切成 10 段，每段叫一个 **limb**（肢节）：

```text
x = v[0] + v[1]·2^26 + v[2]·2^51 + v[3]·2^77 + ... （共 10 项，合计 255 bit）
```

注意指数：26、51、77……相邻差交替是 26、25、26、25……即**偶数下标的 limb 占 26 bit，奇数下标占 25 bit**。平均每个 limb 25.5 bit，所以这套方案外号 **radix 2^25.5**，源自 SUPERCOP 的 ref10 实现，久经考验。

## 为什么不切满 64 bit

直接「5 个 limb 各存 51 bit」不是更省吗？不行，原因在乘法：

- 两个 26-bit limb 相乘 ≈ 52 bit；把 10 个这样的乘积加起来 ≈ 55~56 bit——**还装在一个 u64 里，不溢出**；
- 如果 limb 存到 51 bit，乘积就 102 bit，必须动用 128 位中间值，GLSL 里没有，代码会复杂一个量级。

留出的这些富余 bit 叫 **headroom（净空）**，是整个设计的核心。

💡 **补给：u64 溢出回绕。** Rust 里 u64 加法溢出在 debug 模式直接 panic，release 模式静默回绕（wrap）；GLSL 的 `uint64_t` 永远静默回绕。我们的设计保证中间结果永远不碰 2^64，所以两种行为都不会触发。但做私钥派生时我们**故意**用回绕当特性（splitmix64），Rust 侧必须写成 `wrapping_add` / `wrapping_mul` 明确表达意图，第 4 章会看到。

## 延迟归约（lazy reduction）

还有一个重要约定：limb **允许略超** 26/25 bit。比如加法就是 10 个 limb 分别相加，不立刻进位；只有 limb 大到威胁 u64 溢出之前，才做一次 `carry`（进位，3.4 节）把它压回范围内。

好处：加法不用管进位，快；代价：每个函数都要遵守「输入 limb 不能超过约 2^28」的纪律。我们的代码里这条纪律写在 `Fe` 的文档注释上，第 4 章照抄即可。

## 对照表

| 概念 | 含义 |
|---|---|
| limb | 大数的一段，存在在一个 u64 里 |
| radix 2^25.5 | 10 个 limb，交替占 26/25 bit |
| headroom | limb 里没存数据的富余 bit，留给乘法累加 |
| carry | 把超位的 limb 压回范围的进位操作 |
